# HLD Review — Module: persistence_core (PR #495)

## Summary
The read-path redesign (explicit `usePersistedContentCards`) is a reasonable API shape on its own, but the surrounding write/clear/error-handling design has one critical gap (identity reset never clears the persisted Inbox cache), several architecturally unsound eviction-granularity and coupling issues that the PR's own docs admit are unfixed, and a flag (`usePersistedContentCards`) whose semantics silently diverge at the InboxUI call site from its two siblings.

---

## Design Flaws

### CRITICAL Flaws

**[CRITICAL-1]: `resetIdentities` clears Content Card disk cache but never clears the Inbox disk cache — cross-identity data leak on shared devices**
- **What's Wrong:** `handleResetIdentitiesEvent` (`AEPMessaging/Sources/Messaging.swift:634-650`) calls `clearContentCards()` (lines 652-660), which clears `qualifiedContentCardsBySurface`, `contentCardRulesBySurface`, `contentCardOriginBySurface`, and removes the `CONTENT_CARD_PROPOSITIONS` disk key. It never touches `inboxPropositionsBySurface` or the `INBOX_PROPOSITIONS` disk key. The only place that clears the inbox disk cache is `clearPersistedContentCardAndInboxPropositions()` (lines 662-669), which is reachable **exclusively** through the new opt-in public API `clearPersistedPropositions()` — the app must remember to call it separately. CBE's persisted cache (`codeBasedPropositions` — not present in this module's files, confirmed reverted to memory-only) has no clear path anywhere, but it also has no public read path today, so it is inert rather than a leak vector; Inbox is different because `usePersistedContentCards: true` on `getPropositionsForSurfaces`/`getContentCardsUI`/`getInboxUI` actively reads it back.
- **Why It's Critical:** AEP's identity-reset flow (`MobileCore.resetIdentities()`) exists specifically for shared/multi-user devices (kiosk, retail POS, shared tablets) to guarantee no state leaks across identities. With this gap: User A's inbox content (individually-targeted AJO container-item + linked cards) is written to `INBOX_PROPOSITIONS` on disk while User A is signed in. User A signs out / app calls `resetIdentities()`. User B signs in on the same device. Before any successful network `updatePropositionsForSurfaces` call for User B's inbox surface completes, if the app calls `getInboxUI`/`getPropositionsForSurfaces(..., usePersistedContentCards: true)` — which is exactly the offline/cold-start use case this PR is built for — User A's stale inbox content is served to User B straight from disk. This is a real, observable data-leak path introduced by a feature whose entire purpose is to serve data before the network round-trip that would otherwise naturally re-scope it to the new identity.
- **Evidence:** `AEPMessaging/Sources/Messaging.swift:634-669` (both functions, side by side); confirmed no test exercises this — `grep -n "resetIdentities" AEPMessaging/Tests/UnitTests/MessagingTests.swift` only finds push-token/live-activity-store tests (`testHandleResetIdentitiesEvent_clearsPushTokenAndAllLiveActivityStores`, etc.), none asserting inbox cache state. `AGENTS.md`'s own "Content Card offline — agent summary" table documents `resetIdentities` clearing CC ("**Clears** CC cache … unlike IAM") but is silent on Inbox, suggesting this asymmetry was not consciously decided.
- **Fix Required:** `handleResetIdentitiesEvent` should call `clearPersistedContentCardAndInboxPropositions()` (or an equivalent that also clears CBE, once CBE gets a read path) instead of the narrower `clearContentCards()`, so a reset clears every persisted-and-readable proposition family symmetrically. Add a regression test asserting `INBOX_PROPOSITIONS` is removed on reset.

### MAJOR Flaws

**[MAJOR-1]: Cross-schema-type eviction uses a single `surfacesToRemove` set — self-acknowledged, unfixed stale-disk bug**
- **What's Wrong:** In `applyPropositionChangeFor` (`Messaging.swift`), `surfacesToRemove` is computed once from `requestedSurfaces.minus(returnedSurfaces)` where `returnedSurfaces = Array(inProgressPropositions.keys)` — i.e., surfaces present in the response **across all schema types combined** (IAM + CC + Inbox). That single set is then passed to `cache.updatePropositions`, `cache.updateContentCardPropositions`, and `cache.updateInboxPropositions` alike. If a surface returns IAM data but zero CC propositions (campaign ended CC-side, IAM-side still live on the same surface URI), the surface is not in `surfacesToRemove` at all, so the now-stale CC disk entry is never evicted.
- **Impact:** A future offline read (`usePersistedContentCards: true`) for that surface returns content cards that should no longer exist, because the eviction check is not schema-type-aware. This is not a hypothetical — it is documented and reproduced end-to-end in the repo's own `docs/agents/content-card-offline-known-gaps.md` (Scenario 1), including a suggested fix (compute `ccSurfacesToRemove` from `parsedPropositions.contentCardPropositionsToPersist.keys` instead of the shared `returnedSurfaces`) that was **not implemented** in this PR. The doc rates it "low risk today" only because IAM and CC campaigns conventionally target different surface sub-paths — an operational convention, not an architectural guarantee.
- **Evidence:** `AEPMessaging/Sources/Messaging.swift` — `applyPropositionChangeFor`, the `surfacesToRemove` computation shared across the three `cache.update*` calls; `docs/agents/content-card-offline-known-gaps.md:12-121` (Scenario 1, "Root cause fix (not yet implemented)").
- **Recommended Fix:** Compute a per-schema-type removal set (CC removal from `contentCardPropositionsToPersist.keys`, Inbox from `inboxPropositionsToPersist.keys`, IAM from `propositionsToPersist.keys`) rather than reusing one blended `returnedSurfaces`/`surfacesToRemove` pair for all three disk writes.

**[MAJOR-2]: Non-recoverable-error preservation guard operates at request granularity, not surface granularity**
- **What's Wrong:** `nonRecoverableErrorEventIds` is keyed only by `requestEventId` (`Messaging.swift:38-42`, `handleEdgeErrorResponse`). When flagged, `applyPropositionChangeFor` sets `surfacesToRemove = []` for the **entire** request. `getPropositionsForSurfaces`/`updatePropositionsForSurfaces` accept an array of surfaces in one call, and Edge's `errorResponseContent` event is tagged only with the shared `requestEventId`, not per-surface/scope — so there is no way today to know which surface(s) within a multi-surface batch actually failed.
- **Impact:** For a batched multi-surface request where one surface hits a non-recoverable error and a sibling surface in the same batch legitimately has zero active campaigns, the guard preserves **both** — the sibling surface's stale disk/memory entry that should have been evicted per FR-7 ("a requested surface absent from the response means the campaign is genuinely gone") is incorrectly kept alive indefinitely (until a future request succeeds cleanly with no errors at all). This silently undermines the one correctness guarantee (FR-7) the whole eviction design is built around, specifically for the multi-surface use case the public API explicitly supports.
- **Evidence:** `Messaging.swift` — `handleEdgeErrorResponse` (guard uses `requestEventId` only, no surface/scope disambiguation) and `applyPropositionChangeFor`'s `requestFailed` branch (`surfacesToRemove = requestFailed ? [] : ...`, applied uniformly per request, not per surface).
- **Recommended Fix:** If Edge's error event payload can carry scope/surface information, key the failure tracking per-surface. If it cannot (an Edge-extension contract limitation), this should be documented as an explicit known limitation with a narrower blast radius recommendation (e.g., discourage multi-surface batching when precise per-surface eviction correctness matters), rather than silently applied as a blanket "preserve everything in the batch."

**[MAJOR-3]: `usePersistedContentCards` has materially different semantics at the InboxUI call site than at its two siblings, despite the identical name**
- **What's Wrong:** On `getPropositionsForSurfaces`/`getContentCardsUI`, `usePersistedContentCards` is a **per-call read-source selector** with no side effect on networking — those methods never call the network themselves either way. On `InboxUI`/`getInboxUI`, the same-named parameter is captured as an **immutable `private let`** at `init` time (`InboxUI.swift:99-103`) and permanently locks `performRefresh()` into one of two mutually exclusive modes for the entire lifetime of the object: `true` → every `refresh()` call reads disk only and **never contacts the network again**; `false` → every `refresh()` call always hits the network with **no disk fallback ever**, even on failure. There is no way to construct an `InboxUI` that tries network first and falls back to disk on failure — the exact "Offline"-button pattern this same PR implements for content cards in the demo app (`updatePropositionsWithOfflineFallback()` per `docs/agents/content-card-offline-implementation.md` §6.1).
- **Impact:** An integrator who reads the `getContentCardsUI`/`getPropositionsForSurfaces` docs (flag = "read source for this call") and then applies the same mental model to `getInboxUI` will be surprised: passing `true` at construction does not mean "prefer disk, fall back to network" — it means "never touch the network for this Inbox instance's entire lifecycle." Recovering network capability requires discarding and reconstructing the `InboxUI`. This is a real extensibility/usability trap baked into the API surface, not merely a naming nit — three call sites sharing one flag name are expected by any reasonable caller to share one behavioral contract.
- **Evidence:** `AEPMessaging/Sources/UI/Inbox/InboxUI.swift:99-103` (`private let usePersistedContentCards: Bool`), `performRefresh()` branch (`if usePersistedContentCards { ...never calls updatePropositionsForSurfaces... } else { ...always calls it, no disk read on failure... }`) vs. `Messaging+PublicAPI.swift`'s `getPropositionsForSurfaces(_:usePersistedContentCards:_:)`, which is a stateless per-call parameter.
- **Recommended Fix:** Either rename the InboxUI parameter to reflect its true meaning (e.g., `offlineOnly` / `disableNetworkRefresh`), or redesign it as a per-call parameter on a `refresh(usePersistedContentCards:)` method so its semantics actually match the sibling APIs, or add the missing "try network, fall back to disk on failure" mode so the three call sites converge on one mental model.

**[MAJOR-4]: `clearPersistedPropositions()` name overstates its scope — CBE's persisted cache is orphaned with no lifecycle path at all**
- **What's Wrong:** The public API `clearPersistedPropositions()` (`Messaging+PublicAPI.swift`) reads as "clear everything this SDK has persisted." Its doc comment discloses the gap ("Code-based experience (CBE) persisted propositions are not affected by this call") but the method name does not. Combined with the CBE revert in this PR (no `codeBasedPropositions` read path, no clear path, only a write path left over from the mid-flight design described in `docs/agents/inbox-cbe-offline-handoff.md`), CBE's on-disk cache now has a write-only lifecycle: written on every successful update, read by nothing, cleared by nothing (not `resetIdentities`, not `clearPersistedPropositions()`).
- **Impact:** This is dead weight today (unreadable data sitting on disk indefinitely, growing unbounded across app sessions/surfaces with no eviction path except overwrite-on-next-successful-fetch for the same surface), and it is a trap for whoever re-enables the CBE read path later — they will inherit a cache with no established clear/reset semantics and a public API name (`clearPersistedPropositions`) that already implies broader coverage than it delivers, likely requiring a breaking rename or a confusing scope-widening later.
- **Evidence:** `Messaging+PublicAPI.swift` (`clearPersistedPropositions()` doc comment); `Messaging.swift:664` (`clearPersistedContentCardAndInboxPropositions` — CBE absent); confirmed via `grep` that `codeBasedPropositions`/`CODE_BASED` do not appear anywhere in this PR's shipped `AEPMessaging/Sources` or `AEPMessaging/Tests` diffs (only in the now-superseded design docs), i.e., CBE write-only persistence is real, current, shipped behavior, not a documentation artifact.
- **Recommended Fix:** Either scope the API name accurately (`clearPersistedContentCardAndInboxPropositions()`) or actually clear CBE's disk key too even though it's currently unreadable (cheap, and keeps the name honest); track CBE's write-only-no-clear state as explicit backlog rather than leaving it implicit.

**[MAJOR-5]: Non-recoverable-error classification duplicates Edge's own retry contract with no shared source of truth**
- **What's Wrong:** `MessagingConstants.RECOVERABLE_EDGE_ERROR_STATUS_CODES: Set<Int> = [408, 429, 502, 503, 504, 507]` (`MessagingConstants.swift`) is a Messaging-extension-local hardcoded copy of the status codes Edge's own `PersistentHitQueue` retries. This is the single piece of business logic the entire non-eviction guard (question 4's core mechanism) depends on for correctness.
- **Impact:** If Edge's actual retry policy changes (new recoverable status added, or a status moved between "recoverable"/"terminal"), Messaging's guard silently goes stale with no compiler check, no shared protocol, and no integration test spanning both extensions to catch drift — the two extensions maintain independently-evolving copies of what is supposed to be the same fact. The PR's own research doc (`docs/agents/persistence-write-path-and-errors.md`, "Note: Optimize itself does not do this") confirms `aepsdk-optimize-ios` already has a divergent implementation of the same concept (it records but doesn't gate eviction on it), demonstrating this is a real, already-manifested drift risk across the only two extensions that consume this Edge event today.
- **Evidence:** `MessagingConstants.swift` (`RECOVERABLE_EDGE_ERROR_STATUS_CODES`); `docs/agents/persistence-write-path-and-errors.md:176-183`.
- **Recommended Fix:** This status-code classification belongs in a shared location (e.g., `AEPServices`/`AEPCore`, or an Edge-published constant) that any extension consuming `errorResponseContent` can consume identically, rather than each extension re-deriving its own copy of Edge's retry semantics.

**[MAJOR-6]: Shared `updatePropositionsByKey` cache helper couples the new CC/Inbox write paths to IAM's existing production disk-write behavior**
- **What's Wrong:** `Cache+Messaging.swift`'s `updatePropositions` (IAM) was refactored from a standalone, IAM-specific function into a thin wrapper over a new generic `updatePropositionsByKey` helper, which `updateContentCardPropositions` and `updateInboxPropositions` also call. The refactor is exercised end-to-end by production IAM disk persistence, not just the new features.
- **Impact:** This is confirmed to be more than theoretical: the "spurious remove calls" fix documented in `docs/agents/inbox-cbe-offline-handoff.md` §7 (guarding `try? remove(key:)` behind `!existingPropositions.isEmpty`) changes behavior for **all three** callers of the shared helper, including IAM's already-shipped disk-write path — a change originally motivated by test failures in the new CC/Inbox cache tests silently altered IAM's production `remove()` call frequency as a side effect. Any future bug fix or behavior tweak made in service of the CC/Inbox offline feature now carries blast radius into IAM's mature, already-released persistence path, and vice versa.
- **Evidence:** `AEPMessaging/Sources/ClassExtensions/Cache+Messaging.swift.diff` (single `updatePropositionsByKey` used by `updatePropositions`/`updateContentCardPropositions`/`updateInboxPropositions`); `docs/agents/inbox-cbe-offline-handoff.md:196-210` (bug + fix affecting all three keys through the shared code path).
- **Recommended Fix:** Not necessarily wrong to share the helper (DRY is reasonable here), but this coupling should be called out explicitly in review/test-plan and covered by IAM-specific regression tests whenever the shared helper changes, given IAM's is the one path with real production history and no offline read-path safety net to catch regressions early.

**[MAJOR-7]: `Proposition.offlineAvailable` (per-item gate) is unused dead code — the shipped gate is a single hardcoded global flag instead**
- **What's Wrong:** `Proposition.swift` adds a computed `offlineAvailable: Bool` property that reads `scopeDetails.characteristics.mobileParameters.offline` (defaulting `true`). Per the PR's own design docs (`docs/agents/inbox-cbe-offline-handoff.md` §1.4, `docs/agents/persistence-write-path-and-errors.md`, `docs/agents/write-read-clear-flow.md`, the wiki PRD diffs), this property is supposed to be the **actual gate** controlling whether a given proposition is persisted (`if proposition.offlineAvailable { ...persist... }`). But the shipped `ParsedPropositions.swift` in this diff gates persistence on `MessagingConstants.OFFLINE_AVAILABILITY_ENABLED` — a single hardcoded `true` constant applied uniformly to every proposition, completely ignoring the per-item `offlineAvailable` property. `grep` across the shipped sources confirms `Proposition.offlineAvailable` has exactly one reference in the entire codebase: its own declaration.
- **Impact:** The server-driven, per-campaign opt-out mechanism that the data model (`Proposition.offlineAvailable`) and five separate design docs describe as already wired up does not actually exist in the shipped code — every proposition is persisted regardless of what `mobileParameters.offline` says, silently. This is exactly the kind of blast-radius mismatch the review was asked to check for question 5 (CBE revert leaving half-finished scaffolding): the abstraction (`Proposition.offlineAvailable`) was left in place while its only consumer was swapped out for a coarser global flag, and nothing in the diff calls this out as intentional.
- **Evidence:** `AEPMessaging/Sources/Proposition.swift.diff` (`offlineAvailable` added); `AEPMessaging/Sources/ParsedPropositions.swift.diff` (both persist sites use `MessagingConstants.OFFLINE_AVAILABILITY_ENABLED`, not `proposition.offlineAvailable`); confirmed via `grep -rn "offlineAvailable" AEPMessaging/Sources AEPMessaging/Tests` → single hit (the declaration itself).
- **Recommended Fix:** Either wire `ParsedPropositions` to gate on `proposition.offlineAvailable` (matching what all the design docs already describe as shipped) and remove the app-wide `OFFLINE_AVAILABILITY_ENABLED` override, or remove the unused `offlineAvailable` property and correct the docs to describe the actual (global, hardcoded) gating mechanism. Shipping both — one real, one vestigial — is the "half-finished abstraction" this PR should not leave behind.

### MINOR Flaws

**[MINOR-1]: AGENTS.md-referenced agent docs contradict the shipped code and each other**
- **What's Wrong:** `docs/agents/content-card-offline-implementation.md` (§2.2) documents a 5s/10s dual timeout ("Timeout: 5s default; 10s when `usePersistedContentCards: true`"), but the shipped `Messaging+PublicAPI.swift` uses a single flat `MobileCore.dispatch(event: event, timeout: 5.0)` regardless of the flag (consistent with `getPropositionsForSurfaces` now bypassing the event queue entirely, per `Messaging.swift`'s `handleProcessEvent`). Separately, `docs/agents/card-origin-flag-scenarios.md` still describes an automatic "memory empty → read from disk" fallback ("GET — memory empty → Read persisted cards from disk... 🔵 FLAG SET: disk"), which directly contradicts `docs/agents/write-read-clear-flow.md`'s explicit statement that this PR removed exactly that behavior ("Current implementation (post explicit-flag redesign — no automatic memory-first/disk-fallback)... No automatic fallback. Memory-empty does NOT trigger a disk read on its own anymore").
- **Impact:** `AGENTS.md` explicitly instructs future contributors/agents to read these docs "before you change code" for this exact area. Docs that contradict the shipped implementation and each other will actively mislead the next change, defeating the stated purpose of maintaining them.
- **Suggestion:** Reconcile `card-origin-flag-scenarios.md` with the explicit-flag redesign (or mark it explicitly superseded), and correct the stale 10s-timeout claim in `content-card-offline-implementation.md`.

**[MINOR-2]: `clearPersistedPropositions()` is fire-and-forget with no success/failure signal**
- **What's Wrong:** Unlike `updatePropositionsForSurfacesWithCompletionHandler` and `getPropositionsForSurfaces` (both surface success/failure to the caller), `clearPersistedPropositions()` dispatches an event with no completion handler, and internally both disk removals are `try? cache.remove(...)`, silently swallowing any failure.
- **Impact:** A caller cannot detect or react to a failed clear (e.g., during a compliance-driven "forget this user" flow), and the SDK itself only logs a debug line — inconsistent with the completion-oriented style established by the sibling read/write APIs in this same PR.
- **Suggestion:** Add an optional completion handler (`clearPersistedPropositions(_ completion: ((Bool) -> Void)? = nil)`) mirroring the pattern already used for `updatePropositionsForSurfaces`.

**[MINOR-3]: Inconsistent method-shape convention for the same flag across three call sites**
- **What's Wrong:** `getPropositionsForSurfaces` and `getContentCardsUI` each implement the "with/without flag" surface as two separate overloaded static methods (likely for ObjC-selector reasons on the flagged variant), while `getInboxUI`/`InboxUI.init` implement it as a single method with a Swift default parameter (`usePersistedContentCards: Bool = false`).
- **Impact:** Minor cognitive inconsistency for API consumers/maintainers scanning the three related surfaces; not a functional issue, but at odds with matching the same flag's presentation style across sibling APIs introduced in the same PR.
- **Suggestion:** Pick one convention (overloads vs. default parameter) for all three, documenting the reason if ObjC bridging genuinely requires the split for two of them but not the third.

**Recommendation:** REQUEST CHANGES

| Severity | Count | Action |
|----------|-------|--------|
| Critical | 1 | Must fix before merge |
| Major | 7 | Should fix before merge |
| Minor | 3 | Track for follow-up |

**Summary:** The core API redesign (explicit opt-in disk read, no implicit fallback) is a defensible strategic choice given this is genuinely new persistence capability rather than a change to a shipped behavior — the "silent regression for existing callers" framing does not hold against `main`, since content-card/inbox disk persistence does not exist there at all today. That said, the surrounding write/clear/error-handling design has a real cross-identity data-leak gap in `resetIdentities`, two independently-documented eviction-granularity flaws (one self-acknowledged and unfixed in the repo's own docs), a same-named flag whose behavior diverges at the InboxUI call site from its two siblings, and dead/inconsistent scaffolding left over from the CBE revert and the `offlineAvailable` per-item gate. None of these are exotic or theoretical — each is backed by direct evidence in the shipped diff, the repo's own agent-facing design docs, or both.
