Detailed pros and cons

Inbox context: For getInboxUI, offline requires both the .inbox container-item (layout, capacity, heading) and all linked content card propositions on the same inbox surface (i1). Cards alone are insufficient — partial persistence shows error UI on cold start offline. Authors may forget whether a surface was configured for offline unless the flag is visible at channel/surface level.

Option 1 — Channel configuration (per surface / channel path)

What it is: One checkbox on the Content Cards (or Inbox) channel. All cards — and for Inbox, the container-item plus linked cards — delivered on that surface inherit the same offline policy.

Pros

  • Simple for marketers — set once per feed/surface, not per card.
  • Predictable behavior — every card on home/feed behaves the same offline.
  • Aligns with surface model — SDK keys persistence by surface; channel ≈ surface path.
  • Natural fit for Inbox — one toggle on inbox surface i1 covers container-item and all linked cards together.
  • Easier QA — test offline per surface, not per campaign variant.
  • Lower authoring friction — no per-message decision on every card.
  • Visible surface-level state — authors can see "this surface is offline-enabled" in channel config, reducing "did I cache this?" confusion.

Cons

  • Channel reuse is opaque — same channel can back multiple journeys/surfaces; authors may not know every consumer, so one toggle affects unknown placements.
  • Backward compatibility is risky — changing channel config retroactively changes offline behavior for all live and future campaigns on that channel without per-campaign visibility.
  • Coarse control — can't exclude time-sensitive or personalized cards on the same feed.
  • Cross-team governance — channel owned by platform team; journey authors may not see or control the flag.
  • Migration ambiguity — existing channels: default true vs false when UI ships affects every downstream campaign at once (OQ-3).
  • Inbox still channel-dependent — if authors configure CC channel offline but forget inbox channel i1, offline Inbox errors even when cards exist on disk.

Option 2 — Content / action editor (per card or message)

What it is: Checkbox in the content editor when authoring each card or action.

Pros

  • Fine-grained control — authors opt in/out per message (promo yes, live score no).
  • Explicit intent — offline is a deliberate choice at creation time.
  • Safer for mixed feeds — same surface can mix offline-eligible and online-only cards.
  • Clear audit trail — flag travels with the campaign/journey version in payload.
  • Matches journey mental model — "this specific message should survive offline."

Cons

  • Legacy content gap — older campaigns/journeys have no flag; behavior depends on SDK default (OQ-3: true = silent cache everything; false = nothing offline until re-authored).
  • SDK version skew — customers on older SDK may ignore the flag; same campaign behaves differently by app version.
  • Re-edit burden — enabling offline for existing content requires opening and republishing each message.
  • Authoring fatigue — checkbox on every card; easy to miss or set inconsistently.
  • Inbox complexity — container-item and cards must both be flagged; partial config → error UI offline (see §5.4).
  • Easy to forget cache state — authors may flag individual cards but forget inbox container or linked surface; no single "this surface is cached" view.
  • Weak fit for Inbox UI — Inbox needs container + cards as one unit; per-card flags don't map cleanly to surface-level offline behavior.

Option 3 — Launch / extension configuration (global app policy)

What it is: Checkboxes in Launch (or extension config), e.g. "Offline availability: Content Cards", "CBE", "Inbox". Applies app-wide for that property — all eligible content in that family caches when enabled.

Pros

  • Conscious opt-in — integrator/platform team decides at deploy time; clear ownership.
  • Single switch for rollout — enable offline for entire app without touching AJO campaigns.
  • Backward compatible for authoring — no change to existing campaigns; policy lives in Launch, not message payload.
  • Consistent across SDK versions — once new SDK ships, Launch config drives behavior uniformly.
  • Works before authoring UI — can ship SDK + Launch toggle before AJO UI is ready.
  • No per-message memory burden — authors don't need to remember per-card or per-channel flags.

Cons

  • No per-message control — when enabled, all eligible CC/CBE/Inbox content caches; marketers can't exclude sensitive or ephemeral content.
  • All-or-nothing per surface family — can't mix offline CC with online-only CC in the same app.
  • Launch ↔ AJO disconnect — marketers don't see offline policy in journey UI; "why isn't this updating offline?" support risk.
  • Authors lose cache visibility — no signal in AJO whether a surface or Inbox is cached; only Launch admins know app-wide policy.
  • Multi-app / multi-surface — one Launch property may map to many surfaces; single checkbox may be too broad or too narrow.
  • Inbox same problem at app level — enabling "Inbox offline" caches all inbox surfaces; disabling it breaks all offline Inbox with no per-surface override.
  • Payload vs config split — if flag is Launch-only, server must inject mobileParameters.offline at runtime, or SDK reads Launch directly — extra pipeline work vs Options 1/2.
