PM Q&A — Assurance, Analytics & Timeout (OQ-1, OQ-5)

1. Assurance — when serving from disk?
Emit a debug event on getPropositions / getContentCardsUI completion with propositionSource: memory | disk | none + network status. Also emit when updatePropositions is skipped due to offline (path monitor). Disk hydrate itself is <200ms — Assurance should capture the decision, not every card render.
v1 recommendation: combined read-path event + update-skipped-offline event (visible in Assurance Events tab).

2. Analytics — on display/dismiss/interact?
No for v1. Display/dismiss/interact are campaign engagement metrics — mixing in "served from disk" pollutes AJO reporting. Use a separate operational event (e.g. proposition.cache.served) on disk hydrate / read success if analytics pipeline approves. Assurance can ship first without Edge analytics.

3. 200ms timeout vs 5s — offline vs low network?
These measure different things:

  • Offline (no network): path monitor detects immediately → serve disk in <200ms if app reads cache first and reads are not blocked behind update.
  • Low network (connected but slow): Edge may take 3–10s. A 200ms network timeout would always force stale cache on degraded Wi‑Fi — not recommended as universal timeout.
  • 5s today = Event Hub API callback limit while get waits behind queued update or slow Edge — not disk I/O.

Proposal: offline → skip Edge + cache-first get (sub-second). Low network → optional fail-fast update timeout (3–5s) at Launch/app config, not per-card authoring. Reserve 200ms as disk hydrate target only.
Hybrid (recommended): show disk immediately → background update → refresh UI if network succeeds.
