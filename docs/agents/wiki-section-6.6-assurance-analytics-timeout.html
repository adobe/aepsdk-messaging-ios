6.6 Assurance — when and where to add events (OQ-5)

Goal: During an Adobe Assurance session, integrators and QA can see that content was served from disk (not Edge), why a network call was skipped, and which surface was hydrated.

Note: Disk hydrate itself is fast (<200ms). Assurance should fire at the decision point, not on every card render.

Option A — At disk hydrate completion (recommended primary)

Where: hydrateContentCardRulesEngineFromDisk(for:) — after rules are loaded and the qualified list is built.

Assurance event payload:

text

Pros: Exact moment cache was used; maps 1:1 to SDK behavior.
Cons: Does not explain why hydrate happened (memory miss vs forced offline path).

Option B — At get/read API response (memory vs disk delta)

Where: retrieveMessages / getPropositionsForSurfaces completion — compare:

  • memory had propositions → source: memory
  • memory empty, disk hydrate ran → source: disk
  • both empty → source: none

Pros: Matches what the app actually received; easy for QA ("did Log Props hit disk?").
Cons: Slightly later than hydrate; need to thread propositionSource through the response path.

Option C — At network availability gate (skip Edge)

Where: updatePropositionsForSurfaces when MobileCore.isNetworkAvailable() == false (or health check fails).

text

Pros: Explains why no Edge personalization:decisions event appears in Assurance.
Cons: Does not prove disk content was served — only that network was skipped.

Option D — Combined "proposition source" on every read (A + B)

Emit one Assurance event per getPropositions / getContentCardsUI with:

FieldValues
propositionSourcememory | disk | network | none
networkStatusavailable | unavailable | degraded
surfacesrequested URIs
latencyMsend-to-end callback time

Pros: Single event answers "where did cards come from?" — best for PM/QA demos.
Cons: More implementation work; needs consistent enum across CC/CBE/Inbox.

Recommendation (v1): Ship Option D (combined read-path event) + Option C (network skip on update). Follow Live Activity pattern: EventSource.debug + named events visible in Assurance Events tab.

6.7 Analytics — when and where to add events (OQ-5)

Important distinction: display, dismiss, and interact are campaign engagement events (Edge XDM → AJO reporting). They answer "did the user see/click/dismiss this card?" — not "did the SDK serve it from disk?"

Mixing cache source into display/dismiss/interact pollutes campaign metrics unless Product explicitly wants that.

Option 1 — Separate SDK operational event (recommended)

Where: Same as Assurance Option B/D — on successful disk hydrate or disk-served getPropositions.

Event type: New internal/Edge event, e.g. proposition.cache.served — not tied to display.

Payload: surface, count, source: disk, timestamp, optional lastSuccessfulUpdateAt.

Pros: Clean separation; does not affect display/dismiss/interact counts.
Cons: New schema; needs Product/analytics pipeline approval.

Option 2 — Metadata on existing display event (not recommended v1)

Where: Add XDM field on display track, e.g. meta.propositionSource: "disk".

Pros: Reuses existing pipeline.
Cons: Display count blends disk + network; reporting changes; offline display may never reach Edge anyway.

Option 3 — On dismiss/interact only (weak)

Cons: Misses cards shown but never interacted with; same reporting pollution as Option 2.

Option 4 — App-level analytics only (no SDK change)

Integrator fires their own event when update fails and get succeeds offline.

Pros: Zero SDK schema work.
Cons: Inconsistent across customers; Assurance/debug still needed for Adobe support.

Recommendation:

  • Campaign metrics (display/dismiss/interact): Keep unchanged — user actions only.
  • Operational / offline observability: New proposition.cache.served event (or Assurance-only v1, analytics v1.1).
  • Assurance (debug): §6.6 Option D — can ship without Edge analytics initially.

6.8 Timeout, low network vs offline (OQ-1)

The 200ms and 5s numbers measure different things. Use this framing with Product:

StateWhat device seesSDK behaviorTypical latency
OfflineNo path (airplane mode, no interface)Can skip Edge immediately via path monitor; disk hydrate <200msSub-second if queue not blocked
Low / degraded networkPath "satisfied" but Edge slow or failingStill tries Edge; waits for retries/timeouts3–10+ seconds
OnlineHealthy path + Edge respondsNormal fetch + persistNetwork RTT dependent

Key point: 200ms is the disk-read budget, not a network timeout. Disk hydrate is fast. The 5 second pain is the Event Hub callback timeout while getPropositions waits behind a queued updatePropositions or behind a slow/failing Edge call — not disk I/O.

What fixes what

ProblemFixTarget latency
True offline, empty UI for 5sNetwork gate on update + cache-first get + bypass eventsQueue for reads<200ms–1s
Low network, user waits for EdgeNot solvable with 200ms timeout — network genuinely slow3–10s unless we fail fast
Integrator chains update → get offlineDocument get-first pattern; skip update when offlineSub-second

Should we expose configurable timeout from authoring (like Optimize)?

Short answer: Not for disk serve. Optional fail-fast network timeout for update — different knob.

KnobPurposeSensible defaultAuthoring UI?
Read callback timeoutMax wait for getPropositions response5s (or 10s if disk path)SDK constant; rarely app-config
Update / Edge fail-fast timeoutStop waiting on degraded network3–5s configurableMaybe Launch/app config — not per card
Disk hydrateLoad from persistenceN/A — always fastNo timeout needed

Why not 200ms authoring timeout for "low network":

  • 200ms is below typical Edge RTT on poor Wi‑Fi (Disney parks use case).
  • A 200ms update timeout would always fall back to disk on degraded networks — even when fresh content would arrive in 2–3s.
  • That creates a product tradeoff: stale cache fast vs fresh content slow — PM must choose explicitly, not via a universal 200ms.

Suggested PM language:

Offline vs low network are different problems. When the device has no network, we can detect that locally (path monitor) and serve cached content cards in under 200ms from disk — provided the app reads cache first and we do not block reads behind a network update.

Low network (connected but slow) is not offline. Edge may still take 3–5 seconds or longer. A 200ms timeout would force cache fallback on almost every degraded session, meaning users would often see stale content instead of waiting for fresh campaigns.

The current 5 second timeout is the API callback limit while the SDK waits for Messaging to respond — often because a network update is queued ahead of the read, not because disk is slow.

Proposal:

  1. Offline: network availability check → skip Edge update → serve disk immediately (target sub-second).
  2. Low network: keep configurable update timeout (e.g. 3–5s fail-fast) at app/Launch level — not per message in authoring.
  3. Do not use 200ms as a universal network timeout; reserve 200ms as the disk hydrate performance target only.

Product decision matrix

PM priorityBehavior
Show something immediatelyCache-first get + offline gate; optional short update timeout (2–3s) then refresh
Freshness over speedLonger update timeout (5–10s); accept wait on low network
Hybrid (recommended)Show disk immediately (cache-first); background update with 5s timeout; refresh UI if network succeeds
