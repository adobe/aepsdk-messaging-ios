PM brief — Offline vs low network vs 5 second wait (OQ-1)

Three different things often get mixed up. They need different product decisions.

1. True offline (no network)

The device cannot reach the internet — airplane mode, no signal, or Wi‑Fi with no route. We can detect this immediately on the device; we do not need to wait for Adobe to fail first.

If the user had a successful online session before, content cards can be saved on the device. Showing those saved cards is fast (well under a second once the app asks for them).

User expectation: "Show me what I had last time I was online."

Problem today: Many apps call network update first, then read cards. When offline, the update hangs waiting for Adobe. The read request waits in line behind that failed update. The user sees a blank screen or error for ~5 seconds — even though saved cards were on the device the whole time.

2. Low network (connected but slow)

The phone thinks it is online, but the connection is poor — congested park Wi‑Fi, weak LTE. Adobe may still respond, but it can take 3 to 10+ seconds.

This is not the same as offline. Fresh campaigns may still arrive if we wait long enough.

Why a 200ms timeout is risky as a default: On slow Wi‑Fi, Adobe might return a new promotion in 2–3 seconds. If we give up at 200ms and always show saved (older) content, users on degraded networks would almost always see stale cards, even when fresh content was about to arrive. That is a product tradeoff — speed vs freshness — not a simple technical fix.

Recommended approach: Show saved cards immediately, then refresh in the background when the network responds. User always sees something; UI updates when fresh content arrives.

3. What the 5 seconds actually means (this is not "disk is slow")

When customers report a ~5 second wait or timeout, it is usually not because reading from device storage is slow. Reading saved cards is typically under 200ms.

The 5 seconds is the maximum time the app waits for the SDK to respond to a "get my cards" request. Often the delay happens because:

  • The app asked for a network update first, and the read request is waiting in line behind that update, or
  • The network update is still waiting on Adobe on a slow or offline connection.

Simple analogy: Saved cards are a ready-made meal in the fridge. A network update is ordering delivery. If the app always orders delivery first and will not serve the fridge meal until delivery fails, the user stays hungry for 5 seconds even though food was already in the fridge.

Disk is fast. Waiting in line behind network work is slow.

What we propose

SituationBehavior
OfflineDetect locally → skip unnecessary network call → show saved cards right away
Low networkShow saved cards first → background refresh with a sensible timeout (e.g. 3–5s) → update UI if fresh content arrives
Good networkNormal update flow; 5 second API limit is acceptable

Configurable timeout (similar to Optimize)

Like Optimize sync settings at app/Launch level, we could let integrators choose how long a background network refresh waits before giving up and keeping saved content — e.g. 3 seconds for availability-first apps, longer for freshness-first apps.

This is an app/network policy, not something authors set per content card in AJO.

200ms should be treated as a disk-read performance target, not a universal network timeout.
