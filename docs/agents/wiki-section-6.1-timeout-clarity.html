Key idea: Disk is fast (<200ms). The ~5 second delay is usually GET waiting behind UPDATE on a single-lane queue — not slow disk I/O.

How Messaging processes work today (single-lane queue)

Messaging uses an eventsQueue — one job at a time, in order. Two common jobs:

JobAPIWhat it does
UPDATEupdatePropositionsForSurfacesNetwork call to Edge; wait for Adobe; save to disk on success
GETgetPropositionsForSurfaces / getContentCardsUIReturn cards from memory or disk

Rule today: If UPDATE is in flight, GET waits in line until UPDATE finishes. Disk read itself is fast — GET often never gets a turn before the 5s API timeout.

Good pattern: path monitor detects offline → skip Edge → cache-first GET → cards in <1s.

Scenario 2 — Low network (connected but slow Wi‑Fi)

Path monitor says online, but Edge takes 2–5s+ to respond. A 200ms network timeout would abandon the network call almost every time on degraded Wi‑Fi and force stale cache — even when fresh content would arrive seconds later. That is a product tradeoff (speed vs freshness), not a safe universal default.

Recommended hybrid: show disk immediately → background UPDATE (configurable 3–5s) → refresh UI if network succeeds.

Scenario 3 — Why "5 seconds" is NOT "disk is slow"

Two different numbers:

  • <200ms = time to load and re-qualify cards from disk (when GET actually runs)
  • 5s = max wait for the GET API callback while Messaging is busy — often because GET is queued behind UPDATE or Edge is slow

One-line summary: Disk is fast; the queue and network wait are slow.

Three fixes:

  • Cache-first GET — call get before update so cards render before network work
  • Bypass read queue — disk/memory reads should not wait behind a slow UPDATE
  • Skip UPDATE when offline — path monitor detects no network; don't start a doomed Edge call

Decision guide

  • No network → skip Edge; serve disk immediately (target <1s)
  • Bad Wi‑Fi opening feed → cache-first + configurable UPDATE timeout (3–5s), not 200ms universal network timeout
  • Good network → normal UPDATE then show fresh; 5s callback is acceptable

Is 5 seconds acceptable? Open for product (OQ-1). Target with mitigations above: sub-second offline render when cache exists.
