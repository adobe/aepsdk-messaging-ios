PRD: Messaging Offline Availability — Content Cards, CBE & Inbox (iOS SDK)

1. Executive summary

Problem

Content Cards, Code-Based Experiences (CBE), and Inbox feeds today live primarily in memory. After app restart or offline use, surfaces are empty until the next successful network fetch. In-App Messages already persist to device and reload on cold start. Customers (e.g. Disney — poor park Wi‑Fi) need messaging content from the last good online session available offline.

Proposed solution

Persist eligible proposition rules to device after every successful updatePropositionsForSurfaces. On read, the SDK uses a memory-first, disk-second strategy — no integrator flag required. Whether a proposition is eligible for disk persistence is controlled by an authoring-side offline availability flag delivered in the Edge payload (scopeDetails.characteristics.mobileParameters.offline), with UI placement TBD (see §5.5).

Key decisions

  • No integrator read flag — SDK auto-hydrates from disk when in-memory data is missing or empty for requested surfaces.
  • Memory-first read order — always consult session memory before disk.
  • Separate disk keys per surface family — contentCardPropositions, codeBasedPropositions, inboxPropositions (IAM remains propositions).
  • Save rules, not UI — store Adobe rules; re-run qualification on read so dismiss/expiry still apply.
  • Authoring gate — SDK only persists propositions where server sets offlineAvailable: true (defaults true when absent for backward compatibility).
  • Failed fetch protection — offline/timeout stream close must not mutate any persisted store.
  • Clear on logout — resetIdentities wipes CC/CBE/Inbox memory + disk (PLATIR-62504).

Top risks

  • Authoring flag placement undecided → payload contract may shift.
  • Offline read latency up to 5 seconds in current design when reads are queued behind network updates (see Callout §6.1).
  • Inbox requires both container-item and card propositions — partial persistence shows error UI.
  • Images may not render offline (lazy cache — PLATIR-44800).
  • Dismissed cards may briefly reappear on cold start until event history catches up (Option B disk eviction open).

3. Goals and non-goals

3.1 Goals

  • G1 — Persist eligible proposition rules after successful online fetch (CC, CBE, Inbox).
  • G2 — SDK reads saved content offline via automatic memory-first + disk hydrate (no app flag).
  • G3 — Authoring controls per-proposition offline eligibility via server payload.
  • G4 — No cross-user leakage on shared devices after logout.
  • G5 — Evict stale feeds when server returns nothing for a requested surface (successful update only).
  • G6 — Same read semantics across getPropositionsForSurfaces, getContentCardsUI, and getInboxUI internal reads.

3.2 Non-goals (this PRD)

  • Android / React Native wrapper exposure (follows iOS).
  • Proactive image/asset prefetch for offline (PLATIR-44800).
  • Public clearCachedContentCardPropositions() API (backlog).
  • Detailed engineering file-level implementation (see repo docs/agents/).

6. Callouts & open questions

This section captures product decisions, known behaviors, and unresolved questions. Not implementation detail.

6.1 Callout — Offline content may take up to 5 seconds to appear

Observed behavior: When the device is offline and the app chains updatePropositions → getPropositions (or getContentCardsUI), cached content may not appear for up to 5 seconds — sometimes longer if the update waits on Edge timeout (~10s) first.

Why it happens today:

  • getPropositions events are processed on the same eventsQueue as updatePropositions — a get waits behind an in-flight network update.
  • Public API uses Event Hub 5s callback timeout waiting for Messaging to respond.
  • Disk hydrate itself is fast (<200ms); the delay is queue blocking + timeout, not disk I/O.

Is 5 seconds acceptable? Open for product. Proposed mitigation: process read APIs immediately (bypass queue for gets) + integrator cache-first pattern (get before update). Target: sub-second offline render when cache exists.

6.2 Callout — Memory-first, then persisted storage

Proposed read order (all get APIs):

  1. In-memory cache — session-qualified propositions from current or prior successful update in this session.
  2. Disk hydrate — only when memory is nil or empty for the requested surface; load saved rules, run qualification, populate memory.
  3. Return — qualified propositions or empty array (not error).

No integrator flag. Apps do not choose memory vs disk — SDK decides automatically.

6.3 Callout — Inbox requires container-item AND cards

InboxUI.processInboxPropositions needs both the .inbox container-item (layout, capacity, heading) and individual content card propositions. Caching cards alone is insufficient — offline inbox shows error if container-item is missing.

Validation approach: Simulation tested persisting cards but not container-item → cold-start offline inbox errors as expected. Final behavior requires both to persist when offlineAvailable is true.

6.4 Callout — CBE offline caching (proposed)

Code-Based Experiences (.jsonContent, .htmlContent, .defaultContent) follow the same architecture as Content Cards: separate disk key (codeBasedPropositions), same offlineAvailable gate, same memory-first read via getPropositionsForSurfaces. Host apps render JSON/HTML from returned proposition data.content.

6.5 Callout — Dismissed cards on cold start (Option B)

Dismiss writes dismiss to Event History; journey rules may later insert disqualify. Until then, a dismissed card may briefly reappear when loaded from disk on cold start. Option B (evict from memory + disk on track(.dismiss)) is open — differs from IAM which keeps rules on disk.

6.6 Callout — InboxUI refresh coupling

Today InboxUI.performRefresh chains updatePropositions completion → getPropositions. Network failure does not mean propositions are unavailable if disk has data. Once disk hydration ships, this pattern works if get runs after failed update and hydrates. Long-term: consider decoupling refresh (get first, update in background) — same cache-first pattern as Content Cards.
