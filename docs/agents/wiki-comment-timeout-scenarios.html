PM Q&A — Offline vs low network vs 5s timeout (OQ-1)

Three situations (don't mix them up)

SituationDeviceTypical wait
OfflineNo path (airplane / no route)Disk serve target <200ms–1s
Low networkOnline but Edge slow3–10s+ for fresh content
5s timeout todayOften queued update + slow EdgeAPI callback limit — not disk I/O

Scenario 1 — True offline (e.g. park with no signal; cards saved yesterday)
Bad: update → get chained → GET blocked behind UPDATE ~5s → empty UI / callbackTimeout even though disk has cards.
Good: path monitor skips Edge → cache-first get → cards in <1s. 200ms is realistic for disk read, not network.

Scenario 2 — Low network (connected, congested Wi‑Fi)
Edge may return fresh campaigns in 2–5s. A 200ms network timeout would always fall back to stale cache on degraded Wi‑Fi — product tradeoff (speed vs freshness), not a safe universal default.
Recommended hybrid: show disk immediately → background update (configurable 3–5s) → refresh UI if network succeeds.

Scenario 3 — Why 5s is not "disk is slow"
eventsQueue runs UPDATE before GET; public API waits max 5s for Messaging. Disk hydrate when it runs is <200ms. Fixes: cache-first get, bypass read queue, skip update when offline.

Configurable timeout (Optimize-style analogy)

KnobWhereControls
Update fail-fast timeoutLaunch / app configMax wait for background refresh (e.g. 3–5s)
Get callback timeoutSDK defaultMax wait for getPropositions response (5s today)
Disk hydrateN/AAlways fast — no timeout

Timeout is an app/network policy, not per-card authoring (same pattern as Optimize sync settings).

Decision guide

  • No network → skip Edge; serve disk immediately
  • Bad Wi‑Fi opening feed → cache-first + configurable update timeout (3–5s), not 200ms
  • Good network → normal update; 5s callback is fine
